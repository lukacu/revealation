# Themes and background extensions

Revealation deliberately separates presentation **content and structure** from its visual system. Ordinary users choose curated themes and backgrounds; they do not edit arbitrary fonts, colors, spacing, shadows, CSS variables, or reveal.js theme internals.

The extension boundary is intentionally small and compatible with Revealation's no-build architecture:

```text
presentation content -> semantic layouts -> theme
slide metadata        -> background extension
```

A new visual system should therefore be installed as a theme or background extension rather than added as another editor control.

## Creating a theme

A theme is a directory containing a manifest, CSS, and normally a preview:

```text
themes/
  my-theme/
    theme.json
    theme.css
    preview.svg
    assets/
```

A minimal `theme.json` is:

```json
{
  "id": "my-theme",
  "name": "My Theme",
  "version": "1.0",
  "css": "theme.css",
  "preview": "preview.svg"
}
```

Required fields are `id`, `name`, `version`, and `css`. Theme ids use lowercase letters, digits, and hyphens and start with a letter. `preview` is optional but strongly recommended for the picker. `assets` is an optional array of files relative to `theme.json`; declare files required by the theme so package export can copy them. Resource paths are resolved relative to the manifest.

A theme may guide the background picker without owning any background implementation:

```json
{
  "id": "my-theme",
  "name": "My Theme",
  "version": "1.0",
  "css": "theme.css",
  "preview": "preview.svg",
  "assets": ["assets/texture.svg"],
  "backgrounds": {
    "default": "grid",
    "recommended": ["grid"]
  }
}
```

`backgrounds.default` is optional. `backgrounds.recommended` only orders/highlights independent installed background extensions in the editor; it is not a dependency mechanism.

### Stable design tokens

Theme CSS should set Revealation's `--rv-*` custom properties. These are the supported theme API for ordinary typography, color, spacing, and sizing:

```css
:root {
  --rv-bg: #ffffff;
  --rv-text: #1c1c1c;
  --rv-muted: #777777;
  --rv-accent: #3d62f5;

  --rv-font-heading: sans-serif;
  --rv-font-body: sans-serif;
  --rv-font-mono: monospace;

  --rv-size-title: 2.5em;
  --rv-size-heading: 1.6em;
  --rv-size-body: 22px;
  --rv-size-caption: 0.7em;
  --rv-size-code: 0.68em;

  --rv-slide-padding: 64px;
  --rv-block-spacing: 1em;
  --rv-content-width: 100%;
  --rv-radius: 0px;
}
```

Themes may additionally set reveal.js `--r-*` variables and provide more sophisticated CSS. Prefer deriving reveal.js variables from `--rv-*` tokens so editor, thumbnails, preview, and export use one visual vocabulary.

### Stable semantic classes

Themes may style these Revealation-owned structural hooks:

- `.rv-slide` — every actual presentation slide;
- `.rv-layout-<layout-id>` — the slide's semantic layout, for example `.rv-layout-header-body` or `.rv-layout-two-columns`;
- `.sr-layout` — a registered multi-block layout root;
- `.sr-layout-slot` — a semantic layout slot container;
- `.sr-layout-content` — content inside a layout slot;
- `.sr-align-left`, `.sr-align-center`, `.sr-align-right` — semantic alignment;
- `.sr-media-caption` and its `figcaption` — captioned media;
- `.sr-code` — code blocks generated by Revealation;
- `.rv-block-emphasis` — semantically emphasized paragraph/block;
- `.rv-block-muted` — deliberately secondary/de-emphasized paragraph/block;
- `.rv-block-callout` — highlighted callout block;
- `blockquote` / `.rv-block-quote` — semantic quotation;
- `table`, `thead`, `tbody`, `th`, and `td` — ordinary Markdown tables;
- `.rv-background-host` — background-extension host. Themes may account for it, but should not implement individual effects there.

Every curated theme should provide a coherent treatment for tables and the four semantic block styles. These are content semantics, not arbitrary user CSS: switching themes must keep the same block meaning while changing only its rendering. Theme CSS is loaded in the WYSIWYG editor as well as Present/export, so selectors should normally cover both `.reveal ...` and `.slide-editor ...` where visual parity matters.

Layout definitions remain global and semantic; do not copy or fork a layout definition merely to make it look different in one theme. A theme can radically restyle the same layout through these classes.


### Built-in themes

Revealation currently ships four deliberately distinct curated themes:

- **Clean** — neutral light sans-serif default;
- **Dark** — high-contrast dark sans-serif theme;
- **Classic** — warm editorial palette with Georgia/Palatino-style serif typography;
- **Kinetic** — playful rounded sans-serif typography with violet, coral, teal, and warm accent surfaces.

The different table, emphasis, muted, callout, and quote treatments are useful reference implementations for third-party theme authors: a new theme can change these radically without changing deck content.

### Installing/registering a theme

Revealation is a static, no-build application and browsers cannot portably enumerate directories. Installation is therefore explicit and intentionally simple:

1. add the theme directory under `themes/` (or another app-served location);
2. add one `Revealation.theme.registerManifest(...)` entry in `extensions/themes/register.js`;
3. optionally add a compatibility alias with `registerAlias(...)`;
4. reload the editor.

No theme-specific editor UI code should be needed.

## Editor style boundary

The **Deck settings** dialog is the user-facing home for presentation metadata and curated visual choices. It contains the theme catalog plus presentation-wide motion (slide/background transition and speed) and slide-canvas geometry. These are deck-level settings; themes remain responsible for typography, colors, spacing and semantic layout styling.

Application light/dark mode is intentionally separate in **Application settings** because it changes only the Revealation editor chrome. The slide formatting toolbar exposes curated Background and Layout pickers plus a Notes-sidebar toggle; the Notes sidebar owns Subslide/WIP and speaker notes. No persistent footer settings strip or per-slide transition selector is exposed. Existing per-slide transition metadata continues to load and export, but is a compatibility surface rather than normal UI.

## Creating a background extension

A background is an independent visual extension selected at slide level:

```text
extensions/
  backgrounds/
    my-background/
      extension.json
      background.css
      background.js
      preview.svg
      assets/
```

A static background only needs CSS:

```json
{
  "id": "my-background",
  "name": "My Background",
  "version": "1.0",
  "css": "background.css",
  "preview": "preview.svg"
}
```

For an animated background, add `"js": "background.js"`. As with themes, optional `assets` lists files relative to the manifest so packaged and standalone exports can resolve them reliably.

Background CSS is applied to a dedicated host:

```css
.rv-background-host[data-rv-background="my-background"] {
  background: radial-gradient(circle, var(--rv-accent), transparent 60%);
}
```

Use theme tokens when practical so one background remains compatible with light and dark visual systems.

### Dynamic background lifecycle

Extension JavaScript registers a lifecycle with the small presentation runtime:

```js
RevealationBackgroundRuntime.register('my-background', (element, context) => {
  let frame = 0;

  return {
    start() {
      // Begin animation. Avoid duplicate loops if start() is called again.
    },
    stop() {
      cancelAnimationFrame(frame);
      frame = 0;
    },
    destroy() {
      cancelAnimationFrame(frame);
      frame = 0;
      element.replaceChildren();
    },
  };
});
```

A prototype-style object with `mount(element, context)`, `start()`, `stop()`, and `destroy()` is also supported. The runtime mounts each host once, starts only the active reveal.js slide, stops it when the slide becomes inactive, and destroys removed/replaced hosts when refreshed.

`context` contains `id`, `host`, `reveal`, `presentation`, `assets`, and `asset(name)`. `context.asset(name)` resolves a file declared in the manifest's `assets` array. Extensions must clean up animation frames, timers, event listeners, observers, and inserted DOM in `stop()`/`destroy()` as appropriate.

### Editor versus presentation behavior

The editor loads only background CSS and creates the same `.rv-background-host`; extension JavaScript is **not executed** there. The CSS must therefore provide a useful static preview by itself.

Present/export loads JavaScript only for dynamic backgrounds that are actually referenced by the deck (or are the active theme's default). Leaving a slide calls `stop()`; revisiting it calls `start()`.

### Installing/registering a background

1. add the directory under `extensions/backgrounds/`;
2. add one `Revealation.background.registerManifest(...)` entry in `extensions/backgrounds/register.js`;
3. reload the editor.

No background-specific picker code is required. Do not add general controls for opacity, speed, particle count, CSS, or similar implementation details. If a future extension genuinely needs semantic options, define that as a separate explicit extension contract rather than reflecting arbitrary CSS properties into the UI.

## Persistence

The workspace keeps deck-level settings in `deck.json`; therefore the selected theme is stored once as:

```json
{ "theme": "clean" }
```

Slide backgrounds are semantic separator metadata in `deck.md`:

```markdown
--- layout=header-body background=grid
```

No value is written when the slide uses the normal/theme-default background. Legacy reveal.js `background-color`, `background-image`, `background-video`, and `background-iframe` metadata remains readable for compatibility but is no longer exposed as the normal authoring UI.

## Export behavior

Workspace ZIP export copies the selected theme CSS/assets plus CSS/JS/assets for backgrounds actually used by the presentation. Dynamic backgrounds also include the tiny lifecycle runtime. The exported `presentation.html` references only files inside that package and does not depend on the Revealation editor application.

Standalone HTML recursively inlines the selected theme/background CSS and converts declared extension assets to data URLs where possible. Dynamic extension scripts and the lifecycle runtime are embedded only when required.

Because package export relies on the manifest for non-CSS resources, extension authors should declare runtime assets explicitly. CSS `url(...)` dependencies are recursively inlined by standalone HTML export; for workspace ZIP export, list those local files in `assets` as well.

## Built-ins

The reference distribution currently installs:

- `clean` — the default light theme;
- `dark` — a dark theme using the same semantic structure/tokens;
- `grid` — a lightweight static background extension.

These are intentionally modest examples. The important part is the contract: adding another visual system should mean adding an extension and one registration entry, not expanding the editor into a general-purpose style designer.
